- [ ] **AutoApproveChannel structural guard.** When `adapters/confirmation/auto.py` lands (P1), its `__init__` must assert `os.environ.get("ALLOW_AUTO_APPROVE") == "1"` and raise otherwise. Right now this is only enforced by prose in the spec; this is worth probing directly. — P1 confirmation slice.
- [ ] **Audit committed `fixtures/geocode/` for live entries.** Before runtime paths became configurable, every live cache miss wrote an `AddressRef` (with the user's raw query in `raw`) into the tracked fixtures dir. Live writes now go to `<data dir>/geocode/`, but entries already committed were never reviewed. Check each file against the scenario queries and drop any that are not deliberate fixtures. — runtime-paths slice (out of scope there).
- [ ] **Action-log retention/rotation.** Logs currently grow without bound under `logs/<session>.jsonl`. Add a `make logs-rotate` target and a retention policy doc (likely just "keep last 100 sessions" for the prototype) before any long-running demo. — post-P6.
- [ ] **Scenario YAML top-level `seed` field is unused.** runner.py only consumes `sim.rng_seed`; the top-level `seed` is parsed but ignored. Use it as a single canonical seed source (derive `sim.rng_seed` from it, or remove the top-level field). — T15 Ralph.
- [ ] **Scenario YAML `clock.mode` not validated.** runner.py always constructs FrozenClock regardless of `clock.mode` value. Add a guard that raises if `clock.mode != "frozen"` (interactive mode is a different code path). — T15 Ralph.
- [ ] **`_by_action` raises KeyError on rows missing `action_id`.** All current log rows include `action_id` per invariant 6, but a defensive `.get("action_id", "")` would prevent hard failures if a malformed log is fed to the invariant checkers. — T15 Ralph.
- [ ] **NominatimGeocoder throttle Lock has no concurrency test (T19 review I1).** The current `test_second_call_within_one_second_waits` serializes calls sequentially; a true concurrency test would fire two `asyncio.gather`'d calls and assert the second was delayed ~1s. The Lock could be removed today without test failure. — P3+.
- [ ] **`UberSimAdapter._any_draft_prepared` is a stateful workaround for the surge-on-confirm hook (T28 review).** Once `prepare()` is called, the flag never resets — so a re-prepare-after-rejection on a fresh adapter instance (or a process restart) would not apply peak at re-quote time, creating a behaviour divergence between in-process retries and out-of-process retries. Cleaner: add `on_confirm: bool = False` to `BookingProvider.discover` Protocol (small Protocol rev) or pass context via `Intent.metadata`. The flag works for the `04_surge_on_confirm` scenario today because new drafts are prepared from already-surged options, but the abstraction is fragile. — T28 review.
- [ ] **`UberSimAdapter.confirm()` computes a confirm-time `confirm_price` but persists `draft.option_snapshot` (prepare-time price) on the booking (T28 review).** `last_confirm_price_cents` is a test-only attribute; the booking's stored summary uses the original draft price. For the `price_changed` scenario this is benign (the tool's threshold guard short-circuits before `provider.confirm()` runs when drift exceeds threshold). But if a caller uses the sim directly with `force_surge_on_confirm=True` and the tool's guard is bypassed/disabled, the booking is persisted at the wrong price. Either store `confirm_price` on the booking or remove the dead-code computation. — T28 review.
- [ ] **Appointment-intent hashing.** `intent_hash` raises `NotImplementedError` for `AppointmentIntent`. When the Zocdoc/appointment swap goes from prose to code, mirror the ride hash with appointment-stable fields (subject, location, earliest_at/latest_at bucket). — cross-session-idempotency slice.
- [ ] **Duplicate-intent UX polish.** The `duplicate_intent` outcome carries only `existing_booking_id` + `existing_status`. The agent then has to call `track_booking` or `get_booking` separately to show the user the fare/ETA before asking "book another?". Bundle the existing booking's summary into the `duplicate_intent` outcome payload so the agent can surface it in one turn. — cross-session-idempotency slice.
- [ ] **`MockAppointmentProvider.prepare()` produces drafts without `intent_snapshot`.** The new `confirm_booking` step-3a guard rejects any draft missing a `RideIntent` intent_snapshot. The mock appointment adapter is therefore non-functional through `confirm_booking` until either (a) `MockAppointmentProvider.prepare` is updated to populate `intent_snapshot` with an `AppointmentIntent`, AND `intent_hash` is extended to support appointments, OR (b) the 3a guard is relaxed to a soft fall-back for non-ride intents. The provider-contract suite doesn't exercise `confirm_booking` so the regression is dormant. — cross-session-idempotency slice, code review of T5.

- [ ] **`UberSimAdapter.confirm()` has no internal idempotency guard.** Today it relies entirely on the tool layer's `claim_or_recall` to suppress double-confirm. The provider-contract suite happens to pass because `booking_id = "bk-" + key[:8]` collides deterministically and `put_booking` upserts — accidental, not correct. `MockAppointmentProvider` correctly maintains an internal `_idempotency: dict[str, Booking]`. Mirror that in `UberSimAdapter.confirm` (and `.cancel`) so the contract is honoured at the adapter boundary too, not one layer up. Without this, a direct adapter consumer (future real-Uber SDK migration) double-books. — Design review.
- [ ] **`UberSimAdapter.__init__` types its store as the concrete `SqliteStateStore` instead of the `StateStore` port.** Layer violation: adapters should depend on ports, not other concrete adapters. Easy fix; matters when a second state-store implementation lands. — Design review.
- [ ] **`cancel_booking` lacks the explicit `in_progress` short-circuit that `confirm_booking` has.** `_handle_claim_shortcircuit` handles `in_progress` for confirm; the cancel path falls through to the terminal-status check. A concurrent cancel retry could re-prompt the user instead of cleanly returning the in-flight result. — Design review.
- [ ] **`05_cancellation` scenario does not exercise a non-zero cancellation fee.** The booking is in `requested` status when cancelled and `quote_cancel_fee` returns `Money(0, "USD")`. The four-row pattern and gate invocation are proven; a real fee-quote-and-approve loop is not. Add a sibling scenario (`05b_cancellation_with_fee` or similar) that advances the booking to `en_route` first — requires either an `advance_booking` user turn (the sim already accepts `force_surge_on_confirm`-style hooks) or a scripted state-store seed before the cancel turn. — Design review.

- [ ] **`SqliteStateStore` writes its own `created_at`/`updated_at` via `datetime.now(UTC)` instead of the injected `Clock`.** Three call sites: `claim_or_recall` (state_store.py:218 — hot path on every booking), `put_booking` (~line 137), `put_pending_confirmation` (~line 299). The adapter sits below the tool layer correctly, but invariant 9 says reads of `datetime.now()` should go through the `Clock` port. Under `FrozenClock` scenarios the stored timestamps drift from scenario time. Fix: inject `Clock` into `SqliteStateStore.__init__` (mirror the tool-layer pattern; do **not** add `_override` knobs). — PR #2 review.

- [ ] **Persist `UberSimAdapter._option_cache` (and `_intent_cache`) to SQLite.** Today these caches live on the adapter instance. PR #8 memoizes the adapter per `session_id` in the web app so options survive across turns within a process, but the caches still vanish on restart — a user mid-flow who refreshes between `discover_options` and `prepare_booking` will hit `unknown option_id`. Add an `options` table (or similar) so `prepare()` can re-hydrate from SQLite when the in-memory cache misses, mirroring how drafts/bookings already persist. The provider contract suite should grow a "restart between discover and prepare" test. — PR #8 follow-up.

- [ ] **Cost attribution is session-scoped, not action-scoped.** Gated `outcome` rows (`llm_calls_since_last_action`, `cost_microcents_since_last_action`) report cost since the previous drain of the session's `CostMeter`, not the cost of the action they're attached to. This over-counts (includes every conversational turn since the last gated action — discovery chit-chat, re-quotes, clarifying questions) and under-counts (excludes the current turn's wrap-up call, the largest call of the turn, which happens after the tool returns and so is structurally unattributable by any drain-at-tool-time design) at the same time; a verified probe emitted `4_500_000` microcents where `5_250_000` was actually attributable to that action's turn. Correct attribution needs turn-scoped rather than action-scoped emission, which changes invariant 6's four-row-kind contract — deliberately deferred. — cost-ledger-honesty slice 1.
- [ ] **Two gated `tool_use` blocks in one model response drain the meter once.** If the model emits two gated tool calls in a single response, the first tool to reach `_emit_outcome` drains the meter and takes everything recorded so far; the second tool's drain sees `[]` / `0` regardless of what it actually cost. First-taker-wins, currently untested. — cost-ledger-honesty slice 1.
- [ ] **Web surface permits intra-session turn interleaving into a shared `CostMeter`.** `src/agentic_cab/web/app.py` dispatches turns via `asyncio.create_task` with no per-session serialization, and the human confirmation `await` (`web/channel.py:97`) is a wide interleaving window during which another turn on the same session can record onto (or drain) the same meter. `src/agentic_cab/core/ports.py:163-168` used to claim "the agent loop is single-threaded per session, so no lock is needed" — true for CLI and scenarios, false for web; the comment has been corrected in place to note the web exception. — cost-ledger-honesty slice 1.
- [ ] **Web session tokens and the session registry do not survive a restart, so the startup flush of pending confirmations has no subscriber that can authenticate.** The lifespan hook re-publishes durable `pending_confirmations` rows onto the SSE bus under their original `session_id`, but `_sessions` (and every token) lived in process memory; after a restart `/events` for that id returns 403, and the pending request expires unanswered (a safe denial, but a dead UX path). Fix needs persisted, hashed session tokens or a re-bind flow. — session-bound confirmations slice.
- [ ] **Optionally tighten `gate_invoked_for_tool` to require `channel` on the confirmation dict.** Every real channel now records `channel` (`cli`/`web`/`scripted`) and, on approval, `approver_id`; the scenario checker only requires `approver`. Requiring `channel` too would catch a future channel that forgets to identify itself — deferred to keep the scenario checkers unchanged in this slice; pair it with the next transcript re-render. — session-bound confirmations slice.
- [ ] **`MockAppointmentProvider.discover` seeds its RNG with `hash(seed_str)`, which changes between processes (possible invariant 9 breach).** `src/agentic_cab/adapters/mock_appointment/provider.py:73` builds `random.Random(hash(seed_str) & 0xFFFFFFFF)`; Python randomises `str` hashes per process (`PYTHONHASHSEED`), so the same intent yields different slots across runs. Fix: derive the seed from a stable digest of `seed_str` (e.g. the first 8 bytes of its sha256). Deferred because it changes the mock adapter's output and is outside a lint-only slice. — ruff bandit slice.
- [ ] **A billed-but-unrecorded SDK failure.** `meter.record` in `agent/loop.py:71` is unreachable if `client.messages.create` raises after the request was already billed — the Anthropic SDK retries internally, so a call can cost money and never be recorded on the meter, silently understating every downstream drain. — cost-ledger-honesty slice 1.

## Tests / coverage gaps

- [ ] **`_PHONE` regex deliberately narrowed — does not match bare 7-digit locals or unseparated 10-digit numbers.** PR #15 tightened the regex from `\+?\d[\d\-\(\)\s]{6,}\d` (which false-matched every ISO date) to three explicit shapes: E.164 prefix, NANP parenthesised, plain 3-3-4 with separators. Coverage loss: `555-1234` (7-digit local) and `5551234567` (10 digits no separators) are no longer redacted. Acceptable today because (a) `summary_title` is sourced from `Option.title` ("UberX — ~2 min" etc.) — no real phone numbers enter the log via any structured field, and (b) `pickup`/`dropoff` keys are scrubbed at the structure level via `_redact_address`, not the regex. When a real provider lands that could embed driver phone numbers in freeform strings, audit the regex against representative samples and either broaden or restructure. — PR #15 review.
- [ ] **Consider safelist-based PII redaction.** `redact()` is a denylist scanner today: it walks the payload, treats specific keys structurally (`pickup`, `dropoff`, `summary_title`), and applies the `_PHONE` regex to every other leaf string. A safelist approach — emit only fields named in an allowlist, drop or opaque everything else — would make invariant 8 structurally unbreakable rather than dependent on regex correctness across an open set of providers. Bigger architectural change; trade-off is rigidity vs. evolvability. Worth a design discussion before any new adapter lands that could introduce unfamiliar leaf strings. — PR #15 review.

- [ ] **VCR-style record/replay for Anthropic SDK calls (`@pytest.mark.scenario` + `make transcripts`).** Today the unit + contract suite stubs the SDK directly, so `make verify` is offline and free — good. But the six scenario runs and the live `@pytest.mark.scenario` tests hit the real API on every `make transcripts` and are therefore (a) gated behind a real `ANTHROPIC_API_KEY`, (b) excluded from CI, and (c) cost real money per render. A VCR layer (e.g. `vcr.py` with a custom serialiser for `anthropic.messages.create`, or a thinner hand-rolled cassette under `fixtures/llm/`) keyed on `(model_id, system_prompt_hash, messages_hash, tools_hash)` would: record once with a real key, replay deterministically forever without one, run scenario tests in CI without API access, and let reviewers re-render transcripts byte-identically. Modes: `RECORD` (write new cassettes), `REPLAY` (default; fail on miss), `PASSTHROUGH` (current behaviour). Cassettes committed under `fixtures/llm/<scenario>.jsonl`, regenerated only on intentional model bumps. Aligns with the existing geocode-cache pattern under `fixtures/geocode/` — same record-and-replay shape, same deterministic-by-default ethos. — Engineering hygiene; would also let `make verify` cover behavioural scenarios that today only run on the developer's laptop.

- [ ] **`make lint` does not cover `scripts/`.** It runs `ruff check src tests`; `scripts/` is linted only by the pre-commit ruff hook on staged files, so a ruff upgrade or rule change can leave unstaged scripts with findings that no gate reports. Adding `scripts` to the lint target is a gate change, so it was kept out of the ruff bandit slice. — ruff bandit slice.
- [ ] **Non-bandit `noqa` pragmas carry no reason.** The `S` suppressions all state why; the older ones do not: `T201` in `src/agentic_cab/__main__.py`, `E402` in `tests/scenarios/test_repl_web_parity.py`, and `F401` in `tests/unit/test_harness_smoke.py`. Give each a short reason in the same `# noqa: CODE reason` form. Out of scope for the bandit slice. — ruff bandit slice.
- [ ] **Fingerprint property test: permutations.** Current test only reverses dict insertion order; replace with st.permutations or hypothesis shuffling to cover arbitrary key orderings. — T3 Ralph N1.
- [ ] **Tighten `fingerprint()` parameter type to Option.** Today accepts any BaseModel; spec §4 only requires Option. — T3 Ralph Q1.
- [ ] **Filter `approved_at: null` from declined verified rows.** When the user declines, the `verified.checks.confirmation` dump includes `approved_at: null`. Spec §8 examples only show the field when approved. Consider filtering on the declined path to keep audit rows tight, or update spec §8 to acknowledge the null. — T13 Ralph A5.

## Operational

- [ ] **Committed transcripts predate `approver_id` / `channel`.** `transcripts/*.md` were rendered before `ConfirmationResult` grew `approver_id` and `channel`, so their `verified.checks.confirmation` dicts show only `approved` / `reason` / `approved_at` / `approver`. `make transcripts-ci` validates scenario YAML only, so nothing fails; the next deliberate `make transcripts` re-render (live model calls, model pin unchanged) brings them in line. — session-bound confirmations slice.
- [ ] **Configurable `Secure` flag on the web session cookie.** `cab_session_<id>` is `HttpOnly; SameSite=Strict` but not `Secure`, because `make web` serves plain http on localhost. Any non-localhost deployment must serve TLS and set `Secure` (e.g. a `WEB_COOKIE_SECURE=1` setting threaded into `create_app`). — session-bound confirmations slice.
- [ ] **IPv6 bind hosts are not admitted by the Host allowlist.** Starlette's `TrustedHostMiddleware` strips the port by splitting `Host` on the first `:`, so a bracketed IPv6 host (`[::1]:8000`, or a configured `AGENTIC_CAB_WEB_HOST=::1`) never matches and every request gets 400. Loopback over `127.0.0.1` / `localhost` is unaffected. Supporting IPv6 needs a Host check that parses `[addr]:port` before comparing (and the same parsing for the `Origin` comparison in `web/origin.py`). — host/origin check slice.
- [ ] **A provider or store raise before the gate escapes the tool without emitting an `outcome` row — and now misattributes cost, not just loses it.** A raise from `provider.discover()` or `provider.prepare()` (`tools/confirm.py:321,338`), `provider.quote_cancel_fee()` (`tools/cancel.py:153`), or `channel.request()` escapes the tool before the `try` that guards `_emit_outcome` — a pre-existing invariant-6 gap (no `outcome` row for an action that started). The same gap exists at the store raise sites: `confirm.py`'s `_validate_draft` (306), the intent-hash lookups (356), `claim_or_recall` (372), `release_claim` (413); and `cancel.py`'s `get_booking` (143), `quote_cancel_fee` (153), `claim_or_recall` (161), `release_claim` (238). The cost ledger gives that gap a new symptom: the LLM calls recorded before the raise stay buffered in the `CostMeter` and are drained onto the *next* gated action's outcome row instead, so cost is misattributed rather than merely lost. Fixing it means widening the `try` to cover those provider and store calls, which is a behavior change to the gate flow and deserves its own slice. — P8 final review
- [ ] **`LLMCall.latency_ms` is measured but never emitted; the `executed` row still hardcodes `"latency_ms": 0`.** The branch ships a truthful `latency_ms` on the in-memory `LLMCall` (measured via the new injected `Clock.monotonic_ns`) that is deliberately never emitted, while the `executed` action-log rows at `tools/confirm.py:226,434` and `tools/cancel.py:185,259` still emit a hardcoded `"latency_ms": 0`. The plumbing to fix the `executed` row now exists — a real latency sits unread next to a fake one everything reads. — P8 final review
- [ ] **Load `ANTHROPIC_API_KEY` from a password manager / secret store at process start.** Today the sole secret in `.env` (chmod 600, symlinked from `~/.config/agentic-cab-rides/.env` per README quickstart) is `ANTHROPIC_API_KEY`; optional non-secret overrides documented in `.env.example` (`ANTHROPIC_MODEL`, `NOMINATIM_USER_AGENT`) can stay where they are. That's adequate for a single-developer prototype but has three production-relevant gaps: (a) rotation requires editing a plaintext file in one place — no audit trail, no broadcast to other workstations; (b) no per-user scoping — the same key is shared across every worktree on the laptop; (c) no access log — a stolen-laptop scenario silently grants the key to anyone with shell access. Sketch of the local-dev path with zero code changes: 1Password CLI via `op run --env-file=.env.op -- make repl`, where `.env.op` carries `ANTHROPIC_API_KEY=op://Private/anthropic/credential`; or Bitwarden CLI via `ANTHROPIC_API_KEY=$(bw get password anthropic-key) make repl`. Could add `make repl-op` / `make repl-bw` targets that wrap these. For real deploys: AWS Secrets Manager / GCP Secret Manager with rotation hooks and IAM-scoped reads — a small in-process loader that calls `AsyncSecretsManager.get_secret_value(...)` on startup and refreshes on a TTL. Cross-listed in `docs/WRITEUP.md` §2 "What breaks first in production". — Operational, no code today; revisit before any multi-developer or deploy scenario.
- [ ] **`quote_cancel_fee` before `claim_or_recall` assumes terminal-safe fee quote (T27 review).** UberSim returns `Money(0, "USD")` for terminal bookings; a real provider may raise. The new cancel algorithm calls `quote_cancel_fee` BEFORE `claim_or_recall` (because the deterministic key includes `fee_cents`). When a real adapter ships, contract-test that `quote_cancel_fee` returns gracefully for `_ALREADY_TERMINAL` statuses, or restructure to short-circuit on terminal status before quoting. — T27 review.
- [ ] **Narrow crash window between `consume_draft` and `finalize_idempotency` in confirm_booking (T30 review).** If the process crashes between these two sequential writes, `consumed_at` is set but the idempotency key is unfinalised (`response_blob` is null). On retry, `_validate_draft` returns "draft already consumed" BEFORE `claim_or_recall` can return `"in_progress"` — the agent gets a confusing error instead of the proper in-progress recovery path. No double-booking risk (the key is still claimed), but recovery UX is worse. Fix: make consume_draft + finalize_idempotency atomic in a single transaction, or reorder so finalize_idempotency runs first. — T30 review.
